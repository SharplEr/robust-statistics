В твоём кейсе интерес представляет набор p50/p75/p90/p95/p99, особенно снижение начиная с выбранной части хвоста. Это полноценная постановка с семейством estimands; сводить её к одному mean или median не требуется.

Но quantile всегда относится к конкретной population: всем запросам, только success, только error, одному классу query или фиксированной смеси. Сегодня сосредоточимся на этом различии. Confidence intervals и зависимость разберём отдельно.

Твой рабочий контекст: распределённая БД, latency и time limits. Здесь success/error и hit_limit не считаются синонимами.

01

Распределение в двух направлениях

CDF — cumulative distribution function (функция распределения) — отвечает на вопрос «какая доля запросов укладывается в t?». Quantile function (квантильная функция) обращает вопрос: «какое время покрывает долю p?».

\[\begin{aligned}F(t)&=\mathbb P(T\le t),\\Q(p)&=\inf\{t:F(t)\ge p\}.\end{aligned}\]

Вероятность, приходящуюся на точку или множество, также называют probability mass (вероятностной массой). Формально это значение вероятностной меры на соответствующем множестве.

Для sample (выборки) из n наблюдений ECDF — empirical cumulative distribution function (эмпирическая функция распределения) — строится так: каждый запрос даёт одну ступеньку высотой 1/n.

\[\widehat F_n(t)=\frac1n\sum_{i=1}^{n}\mathbf1\{T_i\le t\}.\]

Здесь \(\mathbf1\{T_i\le t\}\) — indicator function (индикатор): 1, если \(T_i\le t\), иначе 0. Суммируем по всем \(n\) наблюдениям, от \(i=1\) до \(i=n\).

Если значения упорядочены T(1) ≤ ⋯ ≤ T(n), то inverse ECDF даёт:

\[\widehat Q(p)=T_{(\lceil np\rceil)},\qquad0<p\le1.\]

Почему? До ⌈np⌉-го наблюдения накоплено меньше p доли sample; на этом наблюдении F̂ достигает или пересекает p. При ties несколько ступенек совпадают по времени; тот же индекс остаётся верным.

Например, для (10, 20, 40, 80, 160) получаем Q̂(0.9) = T(5) = 160. Это правило без interpolation. Другие conventions могут дать другое число на том же sample — сравнение estimators будет отдельным уроком.

Определение ECDF и её ступенчатая структура: официальная документация SciPy. Формула индекса выше выведена непосредственно из определения; Python и браузер в этом уроке используют именно её.

02

Изменение по каждому quantile (квантилю)

Для одинаково определённых populations (генеральных совокупностей) до и после изменения введём две функции. Shift function (функция сдвига) Δ(p) показывает разность соответствующих квантилей, а ratio function R(p) — их отношение:

\[\begin{aligned}\Delta(p)&=Q_{\mathrm{after}}(p)-Q_{\mathrm{before}}(p),\\R(p)&=\frac{Q_{\mathrm{after}}(p)}{Q_{\mathrm{before}}(p)}.\end{aligned}\]Ratio определён здесь для положительной baseline latency.

Здесь p — уровень квантиля: например, p = 0.95 означает p95. R(p) — безразмерное отношение двух значений времени, а не вероятность. Оно может быть больше 1.

Например, p95 до изменения равнялся 400 ms, а после — 300 ms. Тогда Δ(0.95) = −100 ms, а R(0.95) = 300 / 400 = 0.75: новое значение p95 составляет 75% прежнего, то есть latency на этом квантиле снизилась на 25%.

Интерпретация ratio function при положительной baseline latency.
R(p)Смысл для данного квантиля latency
0.8На 20% меньше прежнего значения
1Значение не изменилось
1.2На 20% больше прежнего значения

В общем виде относительное изменение равно (R(p) − 1) × 100%. Для latency отрицательное Δ(p) означает снижение данного quantile. Так можно описать цель «улучшить начиная с p₀» через Δ(p) на выбранном диапазоне, например p ∈ [p₀, 0.99].

Пять значений — полезная сетка, но не полное распределение. Улучшение оценок p95 и p99 не доказывает improvement между ними; отрицательные sample differences ещё не являются statistical guarantee. Неопределённость для диапазона потребует отдельного рассмотрения.

Также Qafter(p) − Qbefore(p) обычно не равно p-му quantile разностей по paired queries. Первое описывает распределения, второе — изменения у объектов.

Primary reading: Akinshin, Shift and ratio functions и Shift function vs. shift distribution. В уроке направление разности всегда after − before.

04

Причина в conditioning

Когда берём только successful requests, оцениваем не F(t) всех запросов, а conditional distribution (условное распределение):

\[F_{\mathrm{success}}(t)=\mathbb P(T\le t\mid S=\mathrm{success}).\]

До изменения в этом sample 950 элементов: 900 по 30 ms и 50 по 200 ms. Индекс p99 равен ⌈0.99 × 950⌉ = 941; значение на этом месте — 200 ms.

После полного исправления success содержит 1000 элементов. Индекс p99 равен 990; это один из добавившихся тяжёлых запросов по 900 ms. Поэтому p99(success) вырос. При 9 исправлениях индекс равен 950 и ещё указывает на 200 ms; при 10 — 951 и уже на 900 ms.

Это не баг вычисления quantile. Изменилось множество, по которому считается распределение. При этом response time ни одного исходного request ID не вырос; для 50 запросов одновременно улучшились и статус, и response latency.

Условные timings success/error полезны и их стоит сохранять. Для интерпретации изменения нужен контекст состава подгрупп, их долей и фиксированного workload. «Общий p99» также не заменяет статус и полноту ответа.

Аналогично pooled curve может сдвинуться из-за изменения доли тяжёлых query types. Для сравнения самих реализаций понадобится сопоставимый query mix или явно фиксированные веса классов. Этот design разберём отдельно.

Где в этой схеме time limit

В твоей системе hit_limit — отдельная штатная метка, долю которой хочется уменьшить. Поэтому в рабочей постановке будут совместно фигурировать conditional quantile curves, error rate и limit-hit rate. Если есть измеримый эталон полноты, добавим quality при фиксированном budget.

Не будем заранее приравнивать success к complete или hit_limit к error. Observed time-to-response — полноценная метрика, даже если ответ partial. А время, которое понадобилось бы до полного результата, — другой target, иногда недонаблюдаемый из-за остановки.

Это различение targets, а не утверждение, что ваши latency logs автоматически censored. Модель right censoring разберём только после уточнения механизма: NIST: Censoring.

Критерий завершения

Ты можешь вычислить quantile по inverse ECDF и отличить изменение conditional curve от замедления исходных requests.

Отметка локальная; проверка понимания — по твоему объяснению.

Retrieval через 1–3 дня: восстанови пример «950 success → 1000 success» и объясни направление изменения p99 без конспекта. Основное чтение: Akinshin: shift/ratio functions. Все численные данные counterexample придуманы для этого урока.
