Reference / рабочая постановка

Уменьшить хвост.
Сохранить смысл сравнения.

Распределённая БД на Java: top-document queries, aggregation, time budget и неполные ответы. Кейс со слов пользователя; production data здесь нет.

Что известно

  • Dashboard показывает p50/p75/p90/p95/p99. Примерный масштаб: p50 — десятки ms, p95+ — сотни ms.
  • Цель — улучшить верхнюю часть quantile curve начиная с некоторого уровня; квантили выше p99 пока не приоритет.
  • Latency считается отдельно для successful и error requests. Доля time-limit hits считается отдельно; достижение лимита — штатный исход, который хочется минимизировать.
  • При исчерпании бюджета запрос может вернуть неполные top documents или aggregation results. Поэтому полезность оптимизации связана и с полнотой ответа.

Не установлено, как именно partial/complete пересекаются со status success/error. Не считать их эквивалентными категориями.

Цель — несколько связанных объектов

\[\begin{aligned}\Delta_s(p)&=Q_{\mathrm{after},s}(p)-Q_{\mathrm{before},s}(p),\\p&\in[p_0,0.99],\qquad s\in\{\mathrm{success},\mathrm{error}\}.\end{aligned}\]Плюс error rate, hit_limit rate и, при наличии эталона, quality при фиксированном budget.

Диапазон p₀, practical thresholds и guardrails ещё не выбраны. На конечной сетке можно оценить сдвиги выбранных quantiles; утверждение о всём диапазоне сильнее. Совместные confidence statements будут отдельной темой.

Определения shift/ratio: Akinshin. Quantile curves описывают распределение, а не индивидуальное ускорение каждого query.

Три различия, от которых зависит вывод

Conditional latency и состав запросов

p99(success) — quantile условного распределения P(T ≤ t | success). Если после исправления в success попали тяжёлые запросы, он может вырасти при улучшении системы. Проверяемый counterexample в уроке 02.

Query mix и эффективность реализации

Разная доля дешёвых и тяжёлых queries может сдвинуть pooled curve даже без изменения реализации. Для сравнения версий понадобится сопоставимый workload либо условные curves и явно фиксированные веса query classes. Усреднение per-machine p99 не даёт quantile объединённой population.

Time-to-response и time-to-complete

Время до штатного partial response наблюдаемо и имеет собственное распределение. Гипотетическое время до полного результата — иной target. Только в идеализированной модели остановки в фиксированное L наблюдение имеет вид min(Tcomplete, L) вместе с флагом остановки.

В такой модели истинные p99 = 900 ms и p99 = 650 ms при L = 500 ms дадут один и тот же p99 наблюдаемого capped времени — 500 ms. Это собственный пример неидентифицируемости невидимой части tail, а не описание вашего endpoint. Числа за L нельзя восстановить одним limit-hit counter.

Определение right censoring: NIST. В реальной distributed системе граница, cancellation и network overhead могут отличаться от этой идеализации; соответствие модели нужно проверить.

Редкий класс: эффект может быть невидим общему p99

Пользователь предложил stratified analysis (стратифицированный анализ): выделить класс по содержательному критерию запроса, показать улучшение в нём и проверить остальные запросы на недопустимую деградацию. Принадлежность классу определяется устройством запроса, а не самим фактом измеренного ускорения.

Собственный учебный пример: из 10000 запросов 9950 занимают 100 ms, а 50 запросов класса C — 1000 ms. После оптимизации класс C выполняется за 500 ms. По inverse ECDF общий p99 — 9900-е наблюдение — остаётся 100 ms; условный p99 класса C снижается с 1000 до 500 ms. Поэтому улучшение класса с долей менее 1% может быть важным даже без изменения общего p99.

Для решения по реальным данным понадобятся uncertainty (неопределённость), содержательные guardrails (контрольные ограничения) для остальных запросов и сопоставимые нагрузка и quality. Само отсутствие статистически обнаруженного ухудшения не является доказательством, что деградация меньше допустимого порога.

Контроль остальных запросов: дополнение к целевому классу

Если C — класс, который должна ускорять оптимизация, прямой контроль побочных эффектов — запросы вне C, то есть его дополнение. Такая группа определяется тем же содержательным признаком, что C; не требуется находить конкретные запросы «из p99». При неоднородности дополнения полезны отдельные значимые query classes (классы запросов).

Улучшение общего распределения само по себе не доказывает отсутствие ухудшения в каждой группе. Отдельный учебный пример для фиксированных 10000 request IDs:

ГруппаЧисло запросовДо, msПосле, ms
Обычные9800100100
C, целевой класс1001000100
D, другой класс50200400
E, другой класс50500500

В этом наборе все pooled quantiles (общие квантили) уменьшились или сохранились: при сортировке значение после изменения не больше исходного на каждом ранге. Класс C ускорился. Отдельно выбранный самый медленный 1% тоже стал быстрее: до изменения это 100 запросов C по 1000 ms, после — 50 запросов D по 400 ms и 50 запросов E по 500 ms.

Однако D замедлился вдвое. Для дополнения к C inverse-ECDF p99 вырос с 200 до 400 ms: в каждой версии там 9900 запросов, k=ceil(0.99·9900)=9801, а первые 9800 — обычные запросы. Таким образом, проверка дополнения выявляет побочный эффект, который скрыли улучшившиеся общие метрики и улучшившийся верхний 1%.

Это не означает, что любой такой компромисс неприемлем: допустимые изменения задаются целями и guardrails (контрольными ограничениями). Пример показывает логическое различие между общим улучшением и отсутствием деградации остальных групп, а не статистическую значимость результатов случайного эксперимента.

Что именно оценивается внутри верхнего 1%

Отбирать самый медленный 1% отдельно в каждой версии допустимо для сравнения tail distributions (распределений хвоста). Это самостоятельный estimand (оцениваемая величина). Состав запросов может меняться: результат описывает задержки самого медленного процента каждой версии, а не изменение времени одних и тех же query IDs.

Для непрерывной строго возрастающей CDF (функции распределения) F положим a=0.99, qa=Q(a) и рассмотрим T при условии T>qa. Тогда при t≥qa:

\[\begin{aligned}F_{\mathrm{tail}}(t)&=\frac{F(t)-a}{1-a},\\Q_{\mathrm{tail}}(u)&=Q\bigl(a+(1-a)u\bigr),\qquad0<u<1.\end{aligned}\]

Первое равенство следует из P(qa<T≤t)/P(T>qa). Для второго приравниваем условную вероятность u и получаем F(t)=a+(1−a)u.

Квантиль внутри верхнего 1%Уровень в исходном распределении
p50p99.5
p95p99.95
p99p99.99

Это более дальний хвост, чем исходные p95/p99. Для дискретной телеметрии с ties (совпадающими значениями), с point mass (атомом распределения) у лимита или для конечной выборки нужно оговорить правило отбора ровно 1% и округление рангов; приведённое теоретическое равенство не переносится механически на любую реализацию фильтра.

Если цель — проследить одни и те же ранее тяжёлые запросы, зафиксируй query IDs по отдельному разведочному измерению, а эффект оцени свежими измерениями обеих версий. Это другой design (план эксперимента), чем заново определяемый хвост каждой версии; условия сопоставимого workload сохраняются.

Равенства выведены здесь из определения условной вероятности и quantile function (квантильной функции). Общая нормировка truncated distribution (усечённого распределения): SciPy: truncate. В этой постановке отбор хвоста не исправляет ошибки измерения и не является цензурированием.

Декомпозиция latency и квантили этапов

Пользователь предложил отдельно измерять приём запроса, deserialization (десериализацию) из proto и последующую обработку. Это позволяет локализовать вклад сети и вычислений, сохраняя end-to-end latency (полную задержку) для вышестоящих сервисов. Для последовательных непересекающихся этапов одного запроса длительности складываются; для параллельных или перекрывающихся spans (участков трассы) нужна корректная схема учёта.

\[\begin{aligned}T&=T_{\mathrm{receive}}+T_{\mathrm{process}},\\Q_p(T)&\ne Q_p(T_{\mathrm{receive}})+Q_p(T_{\mathrm{process}})\quad\text{in general}.\end{aligned}\]

Проверяемый пример для 10000 запросов и inverse ECDF:

Число запросовReceive, msProcess, msСумма, ms
9840101020
8011010120
8010110120

У каждого компонента p99 равен 10 ms: его медленных значений только 0.8%. Но у суммы p99 равен 120 ms: медленные этапы встречаются у разных запросов и вместе занимают 1.6%. Поэтому компонентные квантили полезны для диагностики, а quantile полной задержки вычисляется по её распределению; для объяснения совместного хвоста полезна связь этапов на уровне request/trace ID.

Числа и расчёты — собственный контрпример из определения inverse ECDF; это не production measurements.

Что уточнять перед inference

  1. Какие workload и load profile сравниваются? Есть ли одинаковые query IDs до/после?
  2. Как пересекаются status, hit_limit и partial/complete? На какой стадии и каким clock измеряется latency?
  3. Каковы deadline policy и sampling window? Сопоставимы ли они между версиями?
  4. Доступны raw events или mergeable histograms? Как агрегируются machines/runs и учитывается dependence?
  5. Есть ли полный эталон для recall@k или ошибки aggregation? Флаг partial и actual quality — разные характеристики.

Эти детали пока не установлены и не блокируют изучение ECDF/quantiles. Они потребуются до выбора конкретной процедуры сравнения production samples.

Про «шумные высокие квантили»

p95/p99 — выбранный практический фокус. Вопрос о стабильности p>0.99 оставляем гипотезой: проверять будем по повторным сопоставимым runs и структуре зависимости, а не по одному числу queries. GC и другие системные паузы могут быть реальной частью latency и не становятся measurement errors только из-за редкости.

Для будущего разбора сбора данных: HdrHistogram: resolution, histogram aggregation и coordinated omission. Здесь нет рекомендации внедрять correction без проверки load generator.
